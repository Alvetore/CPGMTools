## 3. P1 — блокирующие ошибки

### F-01. Авт. огонь ПП не работает на 51–100 м

**Где:** `src/data/cprRules.ts:107-119`, ключ `autofire_smg`, диапазон `"51-100m": null`.

**Факт:** corebook, таблица авт. огня (стр. 173): ПП — `20 / 17 / 20 / 25 / 30` для 0–6, 7–12, 13–25, 26–50, 51–100 м. В коде на 51–100 м стоит `null`.

**Влияние:** `AttackResolverModal.handleRollAttack` (`src/components/combat/AttackResolverModal.tsx:154`) при `targetDv === null` выдаёт «Для этого оружия и дистанции нет допустимой сложности». Валидный выстрел очередью из ПП на 51–100 м невозможно разрешить; в справочнике таблица также показывает пустую клетку.

**Рекомендация:** заменить `null` на `30`, добавить регрессионный тест на всю строку `autofire_smg`, а не только на выборочные значения.

---

### F-02. Дроны из справочника не могут атаковать через резолвер

**Где:** `src/components/reference/GMReferenceView.tsx:880-889`; каталог — `src/data/cprExpandedRules.ts:235-296`.

**Факт:** при добавлении дрона в бой каждое «оружие» создаётся так:

```ts
category: 'Drone Weapon',
damage: '3d6',
```

Но `weaponRangeKey` (`src/data/cprRules.ts:606-617`) не знает категорию `Drone Weapon` и возвращает `undefined`. `AttackResolverModal` требует DV для любой не-melee атаки и отказывает.

Дополнительно:
- у всех дронов урон принудительно `3d6`, хотя в каталоге есть `4d6` (рой, GRAF3) и `3d6` (остальные);
- строка `'Камера кругового обзора'` попадает в массив `weapons` и превращается в оружие с уроном `3d6`;
- объект не соответствует `NpcTemplate` (нет `nameEn`, `armorName`, `skills`, `cyberware`, `gear`), поэтому prop типизирован как `(npc: any, count: number)` — ошибка не ловится компилятором.

**Влияние:** функция «+ В БОЕВОЙ ТРЕКЕР» для дронов создаёт бойца, которого нельзя атаковать штатным резолвером; урон заведомо неверен.

**Рекомендация:** хранить в каталоге структурированные `Weapon[]` с реальными `category`/`damage`/`standardRof`; сенсоры вынести в `gear`; типизировать `onAddNpcToCombat` как `NpcTemplate`; для неизвестной категории давать ручной ввод DV, а не отказ.

### F-03. Таран в погоне требует не ту позицию

**Где:** `src/components/chase/ChaseTrackerView.tsx:147-150`; данные — `src/types/chase.ts:100`; правило — `Interface Kr45n1y v2.0.txt`, стр. 31 (в тексте: таран не происходит автоматически при перемещении в ту же клетку, но требует прямой попытки).

**Факт:** код требует `Math.abs(x.gridSquare - v.gridSquare) === 1` для `m-ram`, то есть соседнюю клетку. Данные и правило требуют одну и ту же клетку. В результате:
- при реальном таране (одна клетка) `target` не находится, выводится «Выберите цель на соседней клетке»;
- при соседней клетке таран разрешён, хотя цель ещё не в контакте.

**Рекомендация:** для `m-ram` искать `diff === 0`; для PIT/Overtake оставить `diff === 1`. Добавить отдельный тест на все три манёвра.

### F-04. Побег не срабатывает, если преследователей не осталось

**Где:** `src/utils/chase.ts:11-14`.

```ts
const pursuers = vehicles.filter(v => v.side === 'pursuer' && !v.isWrecked && !v.isEscaped);
...
pursuers.length > 0 && pursuers.every(...)
```

**Факт:** если все преследователи разбиты или сбежали, `pursuers.length === 0`, и уходящий **никогда** не получает `isEscaped`. Погоня не может завершиться победой уходящего в этом состоянии.

**Рекомендация:** `pursuers.length === 0 || pursuers.every(...)`. Дополнительно рассмотреть завершение погони, когда все преследователи `isWrecked`/`isEscaped`, и явную кнопку «завершить погоню».

### F-05. Количество NPC в бестиарии не ограничено

**Где:** `src/components/bestiary/BestiaryView.tsx:82-85`; input — `:470-475`; цикл — `src/App.tsx:158-185`.

```ts
const setCount = (id, count) => {
  setAddCounts(prev => ({ ...prev, [id]: Math.max(1, count) }));
};
```

**Факт:** `max="12"` у input — только HTML-подсказка, а не ограничение введённого значения. `setCount` не ограничивает сверху. `handleAddNpcToCombat` делает `for (let i = 1; i <= count; i++)` и создаёт комбатантов без лимита. Ввод `100000` заморозит вкладку и попытается записать огромный массив в LocalStorage.

**Рекомендация:** `Math.min(12, Math.max(1, count))` (или явный лимит 50), валидация в `App` перед циклом, сообщение пользователю.

## 4. P2 — существенные ошибки и неполная автоматизация

### F-06. «Стабилизирован» отключён именно при 0 HP

**Где:** `src/components/party/PartyView.tsx:383-386`.

```tsx
<input type="checkbox" checked={member.isStabilized ?? false}
  disabled={member.hpCurrent <= 0 || member.isDead} ... />
```

**Факт:** стабилизация в CPR актуальна при смертельном ранении (0 HP), но чекбокс недоступен именно тогда. При HP > 0 он доступен, хотя стабилизация уже не нужна. В карточке партии нет поля «текущее HP», поэтому персонажа с 0 HP нельзя ни стабилизировать, ни подлечить вне боевого трекера.

**Рекомендация:** разрешить чекбокс при 0 HP (кроме мёртвых) или добавить отдельную кнопку «Стабилизирован (проверка)» с вводом итога; добавить редактирование текущего HP.

### F-07. «Обыск карманов (1d100)» не является 1d100

**Где:** `src/components/reference/GMReferenceView.tsx:362-367`; данные — `src/data/nightCityData.ts:117+`; UI подписан как 1d100 (`GMReferenceView.tsx:393, 2244, 2262, 2269`).

```ts
const item = POCKET_JUNK_TABLE[Math.floor(Math.random() * POCKET_JUNK_TABLE.length)];
```

**Факт:** у предметов есть `roll: 1, 5, 12, 20, 28, 35, 44, 52, 61, 73, 82, 91, 98, 100`, то есть это шкала d100, а не равновероятный список. Код даёт каждому из 14 предметов ~7,1 %, а не ширину диапазона (например, 1–4 = 4 %, 74–81 = 8 %). UI при этом печатает «Бросок 1d100 = [roll предмета]», хотя фактический бросок не выполнялся.

**Рекомендация:** бросить `rollD10`/d100, выбрать последний предмет с `roll <= result`; либо переписать данные в диапазоны `rollMin/rollMax`. Добавить тест распределения/границ.

### F-08. Случайные ситуации 1d100 распределены неравномерно

**Где:** `src/components/reference/GMReferenceView.tsx:245-251`; данные — `src/data/cprExpandedRules.ts:370+`.

**Факт:** таблица содержит диапазоны `1–10, 11–20, 21–30, 31–40, 41–50, 51–65, 66–80, 81–90, 91–100`, а код выбирает `filtered[Math.floor(Math.random() * filtered.length)]`, то есть равномерно по 9 записям. Две записи с шириной 15 должны выпадать чаще; сейчас каждая по ~11,1 % вместо 15 %, остальные — по 11,1 % вместо 10 %. Фильтр по времени суток тоже меняет распределение, но это допустимо; проблема — игнорирование `rollMin/rollMax`.

**Рекомендация:** бросать d100 и искать диапазон; при фильтре по времени сначала отбирать подходящие диапазоны, затем бросать d100 и нормализовать/повторять.

### F-10. Снятие «Автоогонь» оставляет базу Autofire

**Где:** `src/components/combat/AttackResolverModal.tsx:565-568`.

```tsx
onChange={e => {
  setAutofire(e.target.checked);
  ...
  setAttackerSkillBase(attackBase(currentAttacker, { ...activeWeapon, category: `Autofire ${activeWeapon.category}` }, false) ?? ...);
}}
```

**Факт:** обработчик не смотрит на `e.target.checked`. И при включении, и при выключении он пересчитывает базу по категории `Autofire ...`, то есть ищет навык Autofire. Если у персонажа Handgun 6 и Autofire 4, после снятия галочки одиночный выстрел продолжит считаться от Autofire 4 до повторного выбора оружия.

**Рекомендация:** ветвить пересчёт по `e.target.checked` (или вынести в `useEffect` по `autofire`). Добавить тест «включил → выключил → база вернулась».

### F-11. «Подтянуться ближе» ничего не делает

**Где:** `src/components/chase/ChaseTrackerView.tsx:160`; сброс — `src/utils/chase.ts:27`; отображения флага нет.

**Факт:** успешный манёвр ставит `isPulledClose: true`, но:

**Влияние:** манёвр выглядит выполненным, но не даёт заявленного эффекта «нижний край полосы дальности». Это не просто ручная граница: флаг существует, но мёртв.

**Рекомендация:** либо реализовать сдвиг/отображение эффективной дистанции и разрешение melee/абордажа, либо убрать манёвр из автоматики и честно писать «эффект разрешает ГМ».

### F-12. Сетка погони потеряла полосы дальности

**Где:** `src/components/chase/ChaseTrackerView.tsx:281`.

```ts
{trackSquares.map(square => ({ square, range: '', description: 'Относительная координата погони' }))...}
```

### F-13. `canCrit=false`: UI показывает несуществующий +5

**Где:** `src/components/combat/AttackResolverModal.tsx:220-224` и `:849-857`.

**Факт:** `rollDamageFormula` при двух шестёрках выставляет `bonusDamage: 5`. Затем код:

```ts
if (activeWeapon.canCrit === false) dResult.isCriticalInjury = false;
```

Но `bonusDamage` не обнуляется. В результате UI печатает «+5 отдельно в HP», хотя `resolveCprDamage` получает `isCritInjuryRoll: false` и не добавляет +5. Для оружия со спецэффектом без крита это ложная информация.

**Рекомендация:** при `canCrit === false` обнулять `bonusDamage` и `sixesCount` или формировать отображение из фактического `damageResolution`.

### F-14. Два импортёра принимают разные форматы

**Где:** `src/components/common/DataManagementModal.tsx:29-50`; `src/utils/storage.ts:109-118`.

**Факт:** `importPartyMembers` явно поддерживает `{ party: [...] }` (комментарий: «Both import entry points accept single sheets, Export All arrays, and party backups»). **Рекомендация:** вынести определение формата в один парсер и использовать в обоих местах; тест на `{party:[...]}` через верхнюю модалку.

### F-15. Восстановление полного бэкапа без подтверждения

**Где:** `src/components/common/DataManagementModal.tsx:29-35`.

**Факт:** при выборе файла с `exportVersion` сразу вызывается `restoreGmDatabase(data)`, затем alert «успешно». ### F-16. База Восприятия игнорирует модификатор INT

**Где:** `src/utils/storage.ts:142-147`.

```ts

...
perceptionBase = (char.stats?.INT ?? 6) + (pSkill.level ?? 0);
```

**Факт:** у персонажа может быть `statMods.INT` (киберимпланты/биоскульпт). В `stat('INT')` модификатор учитывается, а в `perceptionBase` — нет. ### F-17. Форма энкаунтера может сброситься при перерендере App

**Где:** `src/components/encounters/EncounterFormModal.tsx:50-70`; `src/App.tsx:381`.

**Факт:** effect зависит от `templates`:

```ts
useEffect(() => { ... setNpcs(...); ... }, [initialEncounter, isOpen, templates]);
```

App передаёт `templates={[...OFFICIAL_CPR_BESTIARY, ...customBestiary]}` — новый массив на каждый рендер App. Любой рендер App, пока модалка открыта (например, событие ошибки хранилища, обновление партии, `dataRevision`), меняет ссылку `templates`, effect срабатывает и перезаписывает поля формы значениями `initialEncounter`/пустыми. Незаконченные правки теряются.

**Рекомендация:** мемоизировать `templates` в App/EncountersView или ограничить effect зависимостями `[isOpen, initialEncounter?.id]`; инициализировать форму только при открытии.

### F-18. Энкаунтер можно сохранить с count > 100, но хранилище его отклонит

**Где:** `src/components/encounters/EncounterFormModal.tsx:83, 446`; `src/utils/validation.ts:44` (`n.count <= 100`).

**Факт:** кнопка «+» и добавление из шаблона увеличивают `count` без верхнего предела. `handleSubmit` не проверяет `count`. `saveStoredData` затем отклоняет всю запись `cpgm_encounters`; App показывает общую ошибку «Некорректная структура данных», а в памяти остаётся энкаунтер, который не сохранится.

### F-19. Один повреждённый ключ блокирует сохранение всей базы

**Где:** `src/utils/storage.ts:26-39, 66-79`.

**Факт:** `readDatabase` валидирует **все** ключи при каждом чтении; `saveStoredData` вызывает `readDatabase` перед записью. Если, например, `cpgm_gigs` содержит старую/повреждённую структуру, любое сохранение партии или боя падает, даже если эти данные не читаются. Это осознанная защита от перезаписи повреждённой базы (описана в release-документе), но UX плохой: пользователь не может сохранить ничего, пока не разберётся с чужим ключом.

**Рекомендация:** валидировать/восстанавливать ключи по отдельности, хранить `schemaVersion` и миграции, а повреждённый ключ помещать в `quarantine` с возможностью экспорта. Как минимум — показывать, какой именно ключ сломан.

### F-20. Пробел с автоповтором прокручивает несколько ходов

**Где:** `src/components/combat/CombatTrackerView.tsx:83-92`.

**Факт:** обработчик `keydown` не проверяет `e.repeat`. Если зажать пробел, браузер генерирует повторные события, и бой пролистывается на много ходов вперёд. Это опасно в реальном бою.

**Рекомендация:** `if (e.repeat) return;` и, желательно, `e.preventDefault()` уже есть.

### F-29. Производительность

- Все вкладки в одном бандле: 737 kB / 197 kB gzip. `GMReferenceView` — 2 123 строки, `CombatTrackerView` — 1 255; `React.lazy` по вкладкам даст заметный выигрыш.

## 6. Архитектура и поддерживаемость

**Что хорошо:**
- Строгий `tsconfig` (`strict`, `noFallthroughCasesInSwitch`), всего ~10 `any`-вхождений.
- Единый `cpgm_database_v2` с legacy-миграцией, pending-writes и аварийным экспортом — продуманная защита от quota/partial write.

## 8. Безопасность и деплой
